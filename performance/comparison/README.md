# PHP / native Rust / WASM comparison

This experiment measures personalized HTML rendering from prepared PHP arrays. See [REPORT.md](REPORT.md) for results and limitations. The bridge is experimental benchmark code, not a supported PHP extension.

## Reproduce

Run PHP and Composer inside Docker. Use an otherwise idle **Linux ARM64** machine/container, with a local container filesystem (no macOS bind mount during timing). Record the image ID, CPU model, affinity, PHP version and extensions. The recorded experiment uses PHP 8.4.23, `sail-8.4/app`, image ID `sha256:a14a9d4556cbdef86e1f2866674cb1dea0f18fa8620e49dc89756750a010c599`. That is a locally built Sail image, not a publicly pullable image reference; another build/platform requires new measurements.

1. Build Rust artifacts from the locked dependencies with `bash performance/comparison/build-rust.sh`. It uses the recorded Rust image digest (Rust 1.96.1), ARM64 native and `wasm32-unknown-unknown`, release optimization 3, fat LTO and one codegen unit. Both targets use **the same engine and bridge source**.
2. Prepare PHP dependencies in your PHP container. To restore the measured versions, copy `performance/comparison/results/php-dependencies.lock` to root `composer.lock`, then run `composer install` there. This repository normally ignores root lock files. Do not run dependency installation during timing.
3. Run `python3 performance/comparison/prepare-baseline.py` in the Git checkout. It extracts commit `988a739c20e5e52adbf450f864ce5b4e17e4aa6e` into `build/comparison-baseline` and changes only its namespace, allowing a paired baseline in the same process.
4. Install Extism **1.9.1** in the PHP container. Download `libextism-aarch64-unknown-linux-gnu-v1.9.1.tar.gz` and its published checksum from [the official release](https://github.com/extism/extism/releases/tag/v1.9.1), verify the archive, extract and install `libextism.so` at `/usr/local/lib/libextism.so`. The measured shared library SHA256 is `67019a6afa56ae2b30c252a957e25b9f0c9ab62fb7b373c1bfa44301262ca4e8`. PHP needs FFI, mbstring and OPcache.
5. Copy the repository, vendor, artifacts and generated baseline onto the container's own disk at `/bench`. For example `docker cp . RUNNER:/bench` after creating an otherwise idle runner with `--platform linux/arm64 --cpuset-cpus=4 --entrypoint sleep ... infinity` (choose an existing CPU). Avoid CPU quotas; record them if used. On macOS, avoid AppleDouble files: use `docker cp` or `COPYFILE_DISABLE=1 tar --no-xattrs`.
6. Generate fixtures **inside PHP Docker**: `php -r 'require "performance/comparison/fixtures.php"; echo json_encode(comparisonFixtures(), JSON_THROW_ON_ERROR);' > build/fixtures.json`. Install Ruby `liquid` exactly **5.13.0**, then run `ruby performance/comparison/reference.rb build/fixtures.json build/reference-hashes.json` (Ruby can run on the host; copy files as needed). This must validate 64 contexts. `results/reference-hashes.json` preserves the recorded reference, but regenerate it when fixtures change.
7. Create a dedicated PHP scan directory containing the normal CLI `.ini` files **except both Xdebug and PCOV**. Set `PHP_INI_SCAN_DIR` to it. Disabling coverage at runtime is insufficient; the harness refuses timed execution when either extension is loaded. Verify FFI/OPcache remain loaded.
8. Run `bash performance/comparison/run-series.sh` **inside the runner**, from `/bench`. Do not build, test or profile concurrently. This alternates plain PHP and tracing JIT across three fresh processes each, 30 measured rounds following 10 warmup rounds. It also runs the separate prepared-context control and compatibility probe. Results go to `build/comparison/`.
9. Copy raw JSON results out and summarize with `python3 performance/comparison/summarize.py RESULTS --prefix=final-plain- --output=summary-plain.json`, and repeat for `final-jit-`.

For smoke verification only: `php -d ffi.enable=1 performance/comparison/run.php --paired-baseline --check-only`. All native/WASM artifacts must exist. All scripts use trusted, local fixtures; the C ABI does not implement production input limits or PHP worker lifecycle management.

## Scope and interpretation

- Work begins with prepared PHP arrays and ends with HTML strings. Native and WASM include PHP JSON encoding, crossing FFI, decoding/converting data into Liquid values, rendering, copying output and freeing it. Template parsing/compilation and runtime/plugin startup are outside the timed region for **all** engines.
- Each context varies customer ID, name, segment, wishlist and pricing. Four workloads cover 4-card fragments, 24- and 96-card nested snippets, plus an inline 24-card control. Prices are formatted upstream; Shopify money filters, real merchant themes, database queries and HTTP are outside this contract.
- All 64 inputs must match Shopify Ruby Liquid's output, and every engine must match before timing. A -> B -> A replay checks worker reuse. This is output parity on these fixtures, not proof of full Shopify compatibility.
- Each batch covers all 16 customers, with independently calibrated multiples of 16 calls targeting at least 30 ms CPU; one full cycle may exceed that. Backend order rotates and reverses. Initialization figures are diagnostic and cannot rank cold starts because PHP class loading is shared/sequential.
- Summaries show median of fresh-process medians of **CPU microseconds per render** and process spread. CPU includes user and system time. Paired speedups compare rounds within each process; descriptive 95% cluster bootstrap intervals resample processes and paired rounds (3,000 draws). Three processes are a small sample and intervals do not describe hardware/population uncertainty. Wall time and all samples are retained. **Batch means are not request latency p95/p99.**
- The prepared-context control preloads Rust data and sends only its index; it deliberately removes the per-request PHP-to-Rust conversion. Treat it as an upper-bound architecture control, not as a deployable replacement for the primary path.
- Memory counters are shared-process diagnostic peaks across all engines. They cannot compare per-engine RSS. JIT fields record whether tracing JIT actually activated. Artifact/source hashes and dependency locks identify the tested versions.
- The harness is excluded from the library's level-9 PHPStan scope because it dynamically loads generated baseline classes and C FFI symbols; runtime smoke/parity checks validate those paths. Library source and the existing performance suite remain in the normal analysis scope.
